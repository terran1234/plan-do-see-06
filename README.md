## 인증 구현 설명서 (초안 — ⑤와 5일 기록은 아직 채우는 중)

아래 여섯 항목이 카드 1~5를 묶은 설명서다. 자세한 증거(화면·요청·응답)는 이 문서 아래쪽 카드별 "남긴 것"에 있고, 여기서는 그 위치를 가리킨다.

### ① 무엇으로 붙였나
**인증 서비스 Supabase Auth**(`@supabase/auth-js` 2.117.2)와 **세션 라이브러리 `@supabase/ssr`**(0.12.7), 프레임워크 Next.js 16.4.0이다. 직접 만든 것은 없다. 비밀번호 해시 저장(bcrypt, 비용 10), 토큰 발급·검증, 세션 삭제는 Supabase Auth가 하고, 내 코드는 그 결과를 받아 "로그인했는가", "이 자료가 내 것인가"만 판단한다.

### ② 왜 그걸 골랐나
6번에서 이미 Supabase를 DB로 쓰고 있어서, 사용자 표·비밀번호 해시·토큰 갱신을 따로 만들지 않고 같은 곳의 인증 서비스를 쓰는 편이 비밀번호를 직접 다루는 위험이 가장 적기 때문이다. 함께 검토하고 고르지 않은 방법은 **직접 구현**(해시·세션·만료를 전부 내 책임으로 지게 됨)과 **Auth.js**(이메일·비밀번호 로그인에 사용자 저장소를 따로 만들어야 해서 Supabase와 중복)다. 자세한 이유는 아래 카드 1.

### ⑥ 아직 못 막은 것
"다 막았다"가 아니라 아래는 **아직 못 막았거나 확인하지 못한 것**이다. 각각 왜 위험한지 적는다.

| 못 막은 것 | 왜 위험한가 |
|---|---|
| **무차별 대입**: 비밀번호를 계속 바꿔 가며 시도하는 것을 내가 직접 막지 않는다. Supabase의 기본 제한에 맡겼고 그 동작은 확인하지 않았다 | 쉬운 비밀번호(규칙은 8자 이상뿐)를 쓴 계정은 시도를 반복해서 뚫릴 수 있다 |
| **비밀번호 재설정이 없다** | 비밀번호를 잊으면 계정을 복구할 방법이 없다. 반대로 이메일 확인 없이 재설정을 만들면 남이 내 계정을 가져갈 수 있어 일부러 만들지 않았다 |
| **두 번째 인증 수단(MFA)이 없다** | 비밀번호 하나가 알려지면 계정이 곧바로 넘어간다 |
| **로그를 직접 남기지 않는다**: 로그인 실패·거절된 요청을 앱이 따로 기록하지 않는다(서버 로그에는 요청이 남지만 알림도 분석도 없다) | 공격이 있어도 알아채지 못한다 |
| **가입할 때 이메일 확인을 껐다**(Confirm email 끔) | 남의 이메일로도 가입된다. 가입 화면은 "이미 가입된 이메일입니다"라고 알려 줘 어떤 이메일이 가입돼 있는지 알아낼 수도 있다 |
| **가입이 누구에게나 열려 있다** | 의미 없는 계정이 계속 만들어져도 막지 못한다 |
| **로그인 상태가 자동으로 끊기지 않는다**(세션 만료 설정이 무제한, 무료 플랜은 못 바꿈. 쿠키 400일) | 잃어버린 기기나 남이 쓴 컴퓨터에서 로그인이 오래 남는다 |
| **쿠키에 `Secure` 속성을 따로 붙이지 않았다** | https와 HSTS가 있어 위험은 작지만 쿠키가 https 전용으로 표시된 것은 아니다 |
| **주인 확인이 앱 코드에만 있고 DB의 행 보안(RLS)은 없다** | 앞으로 새 화면·API에서 확인을 빼먹으면 그대로 뚫린다 |
| **비밀번호를 바꾼 뒤 옛 세션이 끊기는지 확인하지 못했다**(변경 화면이 없음) | 바꿨는데 옛 로그인이 살아 있으면 비밀번호를 바꾸는 의미가 줄어든다 |
| 응답 시간 차이처럼 **존재 여부를 간접으로 알아내는 길**은 따져 보지 않았다 | 404로 숨겨도 시간 차이로 남의 자료의 존재를 추측할 수 있다 |

## 카드 1 — 무엇으로 붙일지 고르고, 이유를 적기

### 고른 방식: 인증 서비스 + 세션 라이브러리

| 구분 | 이름 | 버전 | 하는 일 |
|---|---|---|---|
| **인증 서비스** | Supabase Auth | `@supabase/auth-js` 2.117.2 (`@supabase/supabase-js` 2.117.2 안에 포함) | 가입, 비밀번호 해시 저장, 로그인 확인, 토큰 발급·갱신, 로그아웃 |
| 세션 라이브러리 | `@supabase/ssr` | 0.12.7 | 서버(Next.js)에서 로그인 상태를 쿠키로 읽고 쓰기 |
| 프레임워크 | Next.js | 16.4.0 | `proxy.ts`(예전 middleware)로 모든 요청 앞에서 로그인 확인 |

직접 구현은 아닙니다. 비밀번호를 해시해서 저장하는 일과 세션 토큰을 만들고 검증하는 일은 Supabase Auth가 하고, 내 소스는 그 결과를 받아 "로그인했는가"만 판단합니다.

### 왜 골랐나 (한 문장)
**6번에서 이미 Supabase를 DB로 쓰고 있어서, 사용자 표·비밀번호 해시·토큰 갱신을 따로 만들지 않고 같은 곳의 인증 서비스를 쓰는 편이 비밀번호를 직접 다루는 위험이 가장 적기 때문입니다.**

### 함께 검토했지만 고르지 않은 방법
| 방법 | 고르지 않은 이유 (한 문장) |
|---|---|
| **직접 구현** (bcrypt로 해시 + iron-session 같은 암호화 쿠키) | 해시 비용 설정, 세션 만료·갱신, 로그인 시도 제한까지 전부 내 책임이 되고 한 군데만 틀려도 계정이 뚫리는데, 이 과제의 핵심은 인증을 새로 발명하는 것이 아니라 붙인 것을 확인하는 것이라서 뺐습니다. |
| **Auth.js(NextAuth)** (라이브러리) | 이메일·비밀번호 로그인을 쓰려면 사용자 표와 해시 처리를 따로 만들어야 해서, 이미 Supabase에 있는 인증 기능과 중복되는 사용자 저장소가 하나 더 생기기 때문에 뺐습니다. |

| 하는 일 | 파일 |

### 2. 로그인하지 않고 자료 화면 주소를 열었을 때 나오는 로그인 화면
![로그인 없이 첫 화면을 열면 로그인 화면](docs/v3/01-1-login-redirect.png)
로그인하지 않고 `/`를 열었는데 주소가 `/login`으로 바뀌고 로그인 화면이 나온 모습입니다.

같은 일을 요청과 응답으로 적은 기록입니다. (쿠키 없이 요청, 이 컴퓨터에서 `next start`로 띄운 같은 소스, 2026-10-09)

```text
요청 (쿠키 없음)                                           응답
GET /                                                     307 → /login
GET /plans/00000000-0000-0000-0000-000000000000           307 → /login
GET /plans/00000000-0000-0000-0000-000000000000/review    307 → /login
GET /api/export                                           401 {"error":"로그인이 필요합니다."}
POST / (서버 액션 위조: Next-Action 헤더만 붙임)             307 → /login
GET /login                                                200
GET /signup                                               200
```

같은 확인을 **제출 주소(운영 서버)** 에서 다시 했습니다. (쿠키 없이 요청, 배포 직후, 2026-10-09 11:40)

## 카드 2 — 비밀번호를 어떻게 맡아 두는지 보이기

### 고른 방법: bcrypt (Supabase Auth가 적용)
| 항목 | 내용 |
|---|---|
| 되돌릴 수 없게 만드는 방법 | **bcrypt**, 비용(cost) 10 |
| 누가 하나 | 내가 만든 코드가 아니라 **인증 서비스(Supabase Auth)** 가 한다. 내 코드는 비밀번호를 받아 `signUp` / `signInWithPassword`로 넘길 뿐이다 |
| 어떻게 알았나 | 내 말이 아니라 **DB에 저장된 값**의 맨 앞이 `$2a$10$`이다. 이것이 bcrypt(비용 10)라는 표시다 (아래 사진) |

**고른 이유.** 비밀번호를 직접 해시하는 코드를 새로 만들면 비용 설정이나 소금값 처리에서 실수하기 쉬운데, bcrypt는 일부러 계산을 느리게 만들어 무차별 대입을 어렵게 하고 계정마다 다른 소금값을 **자동으로** 붙여 주는 널리 검증된 방법이라서, 내가 따로 만들지 않고 이것을 이미 쓰고 있는 인증 서비스에 맡겼다. (T07-C107: 비밀번호 처리를 직접 만들지 않았다.)

### 저장된 모습 (비밀번호가 글자로 보이지 않음)
bcrypt로 저장된 값은 60글자이고 이런 모양이다. **소금값은 해시와 같은 문자열 안에 함께 들어 있다.** 검사할 때는 저장된 값에서 소금값을 꺼내 입력한 비밀번호에 다시 섞어 비교한다.

```text
$2a$10$ ⟨소금값 22글자⟩ ⟨해시 31글자 …생략⟩
└──┬──┘
 bcrypt, 비용 10
```

DB의 `auth.users.encrypted_password`에서 **앞 29글자(방식·비용·소금값)와 전체 길이만** 읽었다. 해시 본문은 일부러 가져오지 않았다. (공개 저장소에 해시를 통째로 올리면, 비밀번호가 약할 때 밖에서 추측해 볼 수 있기 때문이다.)

![저장된 비밀번호의 앞부분과 길이](docs/v3/02-1-hash-prefix-salt.png)

| 계정 | 저장값 앞부분 | 길이 |
|---|---|---|
| plan1 | `$2a$10$6GcrWiPu…` | 60 |
| plan2 | `$2a$10$vByLgbjk…` | 60 |
| test1234 | `$2a$10$H4kPZvtr…` | 60 |

입력한 글자는 어디에도 보이지 않고, 길이도 모두 60으로 같아서 비밀번호의 길이를 짐작할 수도 없다. (T07-C103)

### 같은 비밀번호로 만든 두 계정은 저장값이 다르다 (T07-C104)
`plan1`과 `plan2`는 **똑같은 비밀번호**로 가입했다. 그런데 소금값 부분이 `6GcrWiPu…`와 `vByLgbjk…`로 서로 다르고, 그래서 저장된 값 전체가 다르다. 한 계정의 비밀번호가 알려져도 같은 비밀번호를 쓴 다른 계정은 같은 값으로 드러나지 않는다.

> 비밀번호 자체는 이 문서에 적지 않았다.

### 로그인 요청과 응답에 원문이 남지 않는다 (T07-C105, C106)
실제 계정의 비밀번호를 쓰지 않고, **가짜 이메일과 가짜 비밀번호**로 운영 주소에 로그인 요청을 보내 응답을 기록했다. (2026-10-09 13:37, 비밀번호는 `●●●●●●●●`로 가렸다)

```text
요청   POST https://plan-do-see-06.vercel.app/login
       폼 값: email = nobody-demo@example.com
              password = ●●●●●●●●        (원문은 기록하지 않음)

응답   303 See Other
       Location: /login?error=이메일 또는 비밀번호가 올바르지 않습니다.
       Cache-Control: no-cache, no-store, max-age=0, must-revalidate
       Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
       Set-Cookie: 없음 (로그인에 실패했으므로)
       응답 크기(본문): 0 bytes

검사   비밀번호 원문이 들어 있는가?
       응답 헤더       0건
       응답 본문       0건
       이동할 주소(URL) 0건
```

- **주소(URL)**: 이동 주소에는 오류 문구만 있고 이메일·비밀번호는 없다.
- **서버 로그**: Vercel 로그에는 시간, 메서드(POST), 상태 코드(303), 경로(`/login`)만 남는다. 요청 본문은 기록되지 않는다. 위 요청도 13:37:12에 한 줄로만 남아 있다. 내 코드에는 `console` 로그 호출이 0개이고, 비밀번호는 `auth-actions.ts`에서 `signUp`/`signInWithPassword`로만 넘어간다.

![Vercel 서버 로그](docs/v3/02-2-vercel-server-logs.jpg)

- **화면**: 비밀번호 입력칸은 `type="password"`라 점으로만 보이고, 오류 화면에도 입력한 이메일·비밀번호를 다시 보여 주지 않는다. (카드 1의 틀린 로그인 화면 참고)
- **쿠키**: 로그인에 성공하면 만들어지는 세션 쿠키는 `httpOnly`로 설정했다 (`lib/supabase-auth.ts`, `proxy.ts`). 브라우저의 스크립트는 읽을 수 없다.

## 카드 3 — 들어온 사람을 어떻게 기억하는지 보이기

### 무엇으로 사람을 알아보나 (T07-C108)
**서버 세션에 묶인 서명 토큰(JWT)으로 알아본다.** 로그인하면 Supabase Auth가 서버에 세션 한 줄(`auth.sessions`)을 만들고, 그 세션에 묶인 **access_token**(서명된 JWT, 60분)과 갱신용 **refresh_token**을 내준다. 앱은 이 둘을 `httpOnly` 쿠키(`sb-<프로젝트>-auth-token`)에 담고, **요청이 올 때마다** 쿠키의 토큰을 인증 서버에 물어 확인한다(`getUser()`, [`lib/auth.ts`](lib/auth.ts)). 쿠키 속 값을 그대로 믿지 않는다.

토큰만 믿으면 로그아웃해도 만료 시각까지 통하기 쉬운데, 서버 세션과 묶여 있어 **서버가 세션을 지우면 만료 전이어도 바로 끊긴다.** 아래 기록이 그 증거다.

### 같은 요청을 로그인 상태와 로그아웃 뒤에 나란히 (T07-C109, C110)
같은 주소(`GET https://plan-do-see-06.vercel.app/`), 같은 방식, **같은 쿠키 값**으로 두 번 요청했다. 두 요청 사이에 한 일은 **로그아웃뿐**이다. (2026-10-09 13:43, `plan1` 계정, [`scripts/session-check.ps1`](scripts/session-check.ps1)로 실행. 토큰·세션 값은 앞 5글자만 보이고 `…생략`으로 가렸다. 비밀번호는 기록에 없다.)

| | 요청 A (로그인 상태) | 요청 B (로그아웃 뒤) |
|---|---|---|
| 주소·방식 | `GET https://plan-do-see-06.vercel.app/` | `GET https://plan-do-see-06.vercel.app/` (**같음**) |
| 쿠키 | `sb-fdellxhmuhlgkbaeenbg-auth-token=base6…생략` | `sb-fdellxhmuhlgkbaeenbg-auth-token=base6…생략` (**같은 값**) |
| 응답 상태 | **200** | **307** → `/login` |
| 내 이메일이 화면에 있나 | 있음 | 없음 |

```text

계정: plan1@naver.com   앱: https://plan-do-see-06.vercel.app

[1] 로그인 성공 → 서버가 세션을 만들어 토큰을 내줌
    access_token  : eyJhb…생략   (서명된 토큰, JWT)
    refresh_token : wlbtn…생략   (새 토큰을 받는 데만 쓰는 값)
    session_id    : 067c3…생략   (서버 DB의 세션 한 줄과 이어짐)

    만료 시각     : 2026-10-09 14:43:28   → 발급 후 3600초(60분)

    GET https://plan-do-see-06.vercel.app/
    Cookie: sb-fdellxhmuhlgkbaeenbg-auth-token=base6…생략   (쿠키 값은 가림. 주소에는 토큰이 없음)
```

### 이 카드에서 아직 못 막은 것
- **로그인 상태가 자동으로 끊기지 않는다.** 세션 전체의 만료(time-box)와 비활동 만료가 "never"이고, 무료 플랜이라 바꿀 수 없다. 계속 쓰면 토큰이 계속 갱신된다. 쿠키도 400일 유지된다.

- **쿠키에 `Secure` 속성을 따로 붙이지 않았다.** 배포 주소는 https이고 Vercel이 `Strict-Transport-Security`(HSTS) 헤더를 보내 http 요청을 막지만, 쿠키 자체가 https 전용으로 표시된 것은 아니다.

- 로그아웃 증거 기록은 **스크립트가 같은 로그아웃 엔드포인트를 호출한 것**이다. 브라우저의 로그아웃 버튼을 누른 장면 자체의 요청·응답은 아니다. (버튼은 카드 1에서 눌러 로그인 화면으로 돌아오는 것을 확인했다.)

## 카드 4 — 남의 자료가 안 열리는 것을 보이기

화면에서 버튼을 숨긴 것이 아니라, **서버가 요청이 올 때마다 주인을 확인**한다. 남의 자료를 읽거나 고치거나 지우려는 요청은 아무것도 바꾸지 않고 **404**로 끝난다. (403이 아니라 404인 이유: 남의 자료가 *있다*는 사실조차 알려 주지 않으려고. 없는 번호와 남의 번호가 똑같이 404다.)

### 서버 로그의 `Date.now()` 오류 조사와 수정
**증상.** Vercel 로그에서, 로그인한 상태로 홈(`/`)과 계획 화면을 열 때마다 `Next.js encountered the unstable value 'Date.now()' while prerendering` 오류 줄이 찍혔다. 화면은 정상(200)이었다.

**원인.** 오류의 호출 경로(`__loadSession` → `_useSession` → `_emitInitialSession`)가 내 코드가 아니라 **로그인 라이브러리(auth-js)** 안이었다. 세션 쿠키가 있으면 만료를 확인하려고 `Date.now()`를 부르는데, 이 앱은 `cacheComponents`와 `partialPrefetching`을 켜 두었고 Next가 로그인한 사람용 화면을 미리 렌더링하는 동안에는 시간 값이 허용되지 않는다. 그래서 **로그인한 상태에서만** 났다.

**수정.** 오류 메시지가 안내한 방법대로, 로그인 클라이언트를 만드는 곳([`lib/supabase-auth.ts`](lib/supabase-auth.ts))에서 `await connection()`을 먼저 부른다. "이 부분은 요청이 올 때 그린다"는 표시라서 미리 렌더링할 때는 여기서 멈추고 실제 요청에서만 실행된다.

**확인(로컬 가짜 서버).** 같은 요청을 보낸 서버 로그에서 `Date.now` 오류가 **44건 → 0건**. 같은 시험(남의 자료 36건)도 **36건 모두 통과**를 유지했다. 정상 사용(내 목록·내 계획·내 돌아보기·내보내기 4요청)은 오류가 0건, 남의 계획 화면 읽기(GET)도 0건이었다.

**만들다가 고친 것.** 처음에는 6번에서 만든 "고칠 점을 다음 계획(할 일)으로 넘기기" 폼으로 규칙을 남기게 했는데, 제출자가 "규칙은 계획이 아닌데 마감일·우선순위·예상 시간이 붙은 할 일이 만들어진다"고 지적했다. 맞는 지적이어서 **규칙 변경을 할 일과 분리**했다. 지금은 새 규칙·이유 두 칸만 받고 할 일을 만들지 않는다. 예상 시간 입력칸도 화면에서 뺐다(어림값이라 쓰지 않음, DB 필수 칸에는 자리표시 값만 넣는다).

**2일차는 늦게 채웠다.** 2026-10-10(토) 낮에는 공부하지 못했다. 그날 기록을 지어내지 않으려고 처음에는 "이 날은 5일에 세지 않는다"고 정리했는데(1일차에 고정한 규칙: 기록이 없는 날은 세지 않고 0분으로 채우지 않는다), 그날 밤에 실제로 1시간을 공부해서 기록을 남겼고 그 기록이 2일차가 됐다. 계획 규칙의 시간표(오전 10시~오후 5시)는 지키지 못한 날이다.

## 카드 3 — 실제로 한 일 적기

### 설계
| 표 | 하는 일 |
|---|---|
| `execution_logs` (실행 기록) | 할 일(`todo_id`)에 이어진 **별도 표**. 시작 시각 · 끝난 시각 · 실제로 걸린 시간(분) · 막혔던 이유 · 요청 키(`request_key`, 유일) |
| `completions` (완료 기록) | 완료할 때마다 한 줄. 되돌리면 `reverted_at`만 채워 이력을 남김. 요청 키(`request_key`, 유일) |

- **계획을 덮어쓰지 않음**: 실행 기록은 `execution_logs`에만 쓰고 `plans`/`todos`의 계획 값(마감일·우선순위·예상 시간)은 건드리지 않습니다. 화면에는 계획의 "예상 시간"과 실행 기록의 "실제 합계"를 나란히 보여 줍니다.
- **완료 중복 방지 (DB가 막음, 버튼 잠금에 기대지 않음)**
  1. 화면이 만들어질 때마다 폼에 **요청 키**(UUID)를 넣고, 같은 키의 완료 요청은 DB `unique(request_key)`로 한 번만 받습니다.
  2. 키가 달라도 `unique (todo_id) where reverted_at is null` 인덱스 때문에 한 할 일에 **열린 완료 기록은 하나뿐**입니다.
  3. `complete_todo()` DB 함수가 할 일 행을 잠근 채(`FOR UPDATE`) 한 트랜잭션에서 처리하므로 동시에 눌러도 순서대로 처리됩니다.
- **돌아보기의 완료 수**: 할 일 표가 아니라 **열린 완료 기록**(`completions`)에서 직접 셉니다. 숫자를 누르면 `상태: 완료`로 거른 목록으로 이동합니다.

## 카드 4 — 돌아보기, 그리고 다음 계획으로

화면: `/plans/[계획 ID]/review` (계획 화면의 "돌아보기 화면으로" 링크)

### 집계 기준 (화면에도 같은 문장이 적혀 있음)
대상 = 마감일이 고른 기간(시작~끝, 기본은 계획 전체 기간) 안에 있는 할 일. 지운 할 일은 DB에 없으므로 자연히 빠집니다.

| 숫자 | 계산 | 통과 기준 |
|---|---|---|
| 계획 수 | 대상 할 일 수 | T06-C28 |
| 완료 수 | 그중 지금 완료 상태 | T06-C29 |
| 지연 수 | **완료가 아니고** 마감일이 서울 시간 오늘보다 앞. 완료한 할 일은 늦었어도 지연으로 세지 않음(완료로만 셈) | T06-C30 |
| 막힘 수 | 막힌 이유가 적힌 실행 기록이 하나라도 있는 **할 일 수** (같은 할 일에 막힘이 2건이어도 1) | T06-C31 |
| 예상 시간 | 대상 할 일의 예상 시간 합계 | T06-C32 |
| 실제 시간 | 그 할 일들의 실행 기록 합계 (기록이 없으면 0) | T06-C32 |
| 차이 | 실제 − 예상 (둘 다 **분**으로 맞춰 계산, 아무것도 없으면 0) | T06-C32 |

- 계획 화면의 요약에 있는 "막혔던 기록 N건"은 *실행 기록* 개수이고, 돌아보기의 "막힘 수"는 *할 일* 개수입니다. 단위가 달라서 이름도 다르게 붙였습니다.
- 주별(월요일 시작) 비교 표도 있고, 주별 합계는 전체와 항상 같습니다(같은 할 일을 두 번 세지 않음).

### 숫자 → 근거 기록 (T06-C83)
집계의 모든 숫자(전체 · 주별)가 링크입니다. 누르면 같은 화면 아래 "근거 기록"에 그 숫자를 이루는 할 일이 나오고, 할 일 이름을 누르면 계획 화면의 해당 할 일로 이동합니다.
- 계획·완료 수 → 해당 할 일 목록
- 지연 수 → 마감이 지난 할 일과 "N일 지연"
- 막힘 수 → 막힌 이유와 시각이 적힌 실행 기록
- 예상·실제·차이 → 할 일별 예상 vs 실제 + 실행 기록 목록 (기록 없는 할 일은 "실제 0으로 계산"이라고 표시)

### 고칠 점 한 줄 → 다음 계획 (T06-C33)
- 돌아보기 화면 아래 폼에 고칠 점 **한 줄**과 다음 계획의 마감일·우선순위·예상 시간을 적고 "다음 계획으로 넘기기"를 누릅니다.
- DB 함수 `carry_review()`가 **한 트랜잭션**으로 ① `reviews`에 고칠 점 + 그 시점 집계 숫자(snapshot) 저장 ② 새 할 일을 만들고(`source_review_id`로 돌아보기와 이음, 태그 `돌아보기`) 합니다.
- 같은 기간은 한 번만 넘어갑니다 (`unique(plan_id, period_from, period_to)`, 돌아보기 하나당 할 일 하나). 두 번 눌러도 1건.
- 넘어온 할 일에는 계획 화면에서 "돌아보기에서 넘어온 고칠 점" 표시가 붙습니다. 스냅샷은 서버가 DB에서 다시 계산해 저장하므로 폼 값을 조작할 수 없습니다.

### 확인한 결과

3. **무엇이 보이면 통과인가요**: 모든 화면 위의 노란 공개 안내, 계획·할 일 5개 이상·실행 기록 3개 이상, 0이 아닌 돌아보기 숫자와 숫자를 누르면 나오는 근거 기록, 넘어온 "고칠 점" 할 일, 새로고침해도 그대로인 값, 내려받아지는 JSON 파일 하나.
4. **안 될 때는 무엇이 보이나요**: 목록을 못 읽으면 빨간 글씨 "…불러오지 못했습니다. 잠시 후 다시 시도하세요", 입력이 틀리면 칸 위에 빨간 안내(예: "끝난 시각이 시작 시각보다 빠릅니다"), 완료를 중복해 누르면 "이미 완료된 할 일입니다. 완료 기록은 한 건만 남습니다."

### AI와 내 판단 (3줄)
1. **AI에게 맡긴 일**: 앱 설계·구현(Next.js + Supabase + Vercel), DB 표·제약·함수 작성, 저장소·DB·배포 설정 조작, 테스트와 증거 화면 촬영, README 작성, 그리고 돌아보기 "고칠 점" 한 줄을 내 기록에서 골라 문장으로 만드는 일.
2. **내가 직접 판단한 일**: 어떤 계획을 쓸지(정보처리기사 실기, 주 5회·10/25까지·평일 5시간·우선순위 높음), 할 일 7개가 맞는지 확인("그대로 OK"), 내가 실제로 공부한 기록 3건의 시간과 막힌 곳, 추천 기술 조합을 받아들일지, 새 Supabase 프로젝트를 만들지, GitHub 앱 권한·본인 확인·비밀 키 입력 같은 보안 단계를 직접 처리, 증거 촬영을 모든 카드가 끝난 뒤 한 번에 하기로 한 것.
3. **AI 제안을 따르지 않은 일**: (a) 저장소 생성과 환경 설정을 직접 하라는 AI의 제안을 따르지 않고 AI가 대신하게 요청함, (b) 고칠 점 한 줄을 직접 정하라는 AI의 권유를 따르지 않고 AI가 내 기록에서 골라 넣게 함.
